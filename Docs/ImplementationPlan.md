**Verified 2026-08-08 (in-browser, dev build):** the live v4 playtest save migrated to v5 in place. With the tier granted but no ITERATION BUDGET EXTENSION, `for i in range(50)` was refused before running — identical wording in the terminal and as an inline editor underline on the `50` ("This process can repeat at most 10 times, and this loop asks for 50"). After installing the extension the limit read 100, and a deliberately wasteful `every 1 seconds { for i in range(100) { process_job() } }` deployed and was preempted on **every** activation: monitor `8 RUNS`, profiler `200 OPS AVG // 344.0 COMPUTE // 100%`, and the report **PREEMPTED — "8 of 8 activations ran out of the 200-op execution budget before finishing, spending 344.0 compute on work that was thrown away."** Installing the EXECUTION BUDGET EXTENSION the report suggests raised the budget to 500, cleared the preemption, and surfaced the _next_ real problem — the profiler switched to **STARVED** with 217 of 230 requests rejected, which is the loop asking for 100 jobs from a queue that holds 60. The execution log recorded one line per activation (`PROC-01 every 1 seconds // 301 OPS // 65.05 COMPUTE // 100 CMD // 96 REJECTED`) and never flooded. The new BATCH DRAIN template generated `every 3 seconds { for i in range(5) { if … } }`, deployed and ran clean at 36 ops per activation. Layout checked at 1280 px and 440 px (no horizontal page scroll, no overflow). 201 tests (37 new). One defect found and fixed during verification: the diagnosis denominator double-counted aborted activations ("8 of 16").

## M7 — Temperature + overheating challenge (GDD §26 Thermal Runaway-lite)

**Goal:** Code has physical consequences; the first feedback-control puzzle.

| Task                       | Detail                                                                                                    | Status |
| -------------------------- | --------------------------------------------------------------------------------------------------------- | ------ |
| Heat model                 | Heat from compute use, passive + purchasable cooling, efficiency degradation curve (TDD §4.3)             | 🟢     |
| Thermal watchdog           | Hard-threshold shutdown halting scripts/workers with diegetic messaging                                   | 🟢     |
| Heat controls              | `reduce_clock_speed()`, `boost_cooling()` commands + `stats.temperature`                                  | 🟢     |
| Overheating challenge beat | A demand spike makes max-throughput overheat; player must control it (manually, then via `when` script)   | 🟢     |
| Oscillation is possible    | A naïve bang-bang cooling script visibly wastes energy — groundwork for GDD feedback-instability teaching | 🟢     |

**Acceptance:** The challenge is failable, recoverable, and solvable elegantly with a small script; solving it with a script feels clearly better than hand-managing it.

**Verified 2026-08-09 (in-browser, dev build):** the live v6 playtest save migrated to v7 in place and was restored afterwards through the new dev-handle helper (OP-7). A fully built-out sandbox rested at **65.4 °C, NOMINAL, 100% throughput** in calm conditions — warm but never degraded, which is the pin that stops a player being cooked by their own shopping list. The first priority demand window opened on schedule with `FACILITY ADVISORY // PRIORITY BATCH WINDOW OPEN // SHARED COOLANT LOOP DERATED // INBOUND RATE ELEVATED`; uncontrolled, the core reached **91.9 °C peak**, throughput degraded to 74%, and the watchdog tripped **twice** (`THERMAL WATCHDOG // CORE AT 92.1°C // NODE HALTED`), releasing at the resume threshold each time. While halted, EXECUTE and RUN were both refused with `REJECTED // THERMAL WATCHDOG ACTIVE // NODE HALTED`, the panel read `CORE STATE // HALTED — WATCHDOG`, both levers were disabled and the temperature bar switched to its alert fill. Deploying the generated **THERMAL GOVERNOR** template (plus a `buy_energy` top-up, because the coolant draws more power than the sandbox generates) held the next window at a **69.0 °C peak with zero trips, 100% throughput throughout, 4 coolant starts and 130 energy**, and produced **27% more requests per second** than the uncontrolled run. Manual levers fill the same actuators at the same prices (`> BOOST_COOLING` → `COOLANT LOOP OPEN`, −10 energy spin-up, 4 s hold). Binding gating checked: before the tier, 7 reads and 8 commands; after, 8 and 10, with `stats.temperature` itself never gated because the heat model runs from tick 0. Save/load round-trips the thermal state exactly. Layout clean at 1280 px and 440 px (no horizontal overflow; the two levers sit side by side at 185 px each on the narrow screen), no console errors. 285 tests (35 new). Screenshots were again unavailable (the Browser pane was not compositing); verification is via the DOM, the snapshot and the console.

**Oscillation, measured (the "wastes energy" deliverable):** the same script at two polling intervals, across one window — `every 1 seconds` re-arms the coolant before it lapses and runs as one engagement (**7 spin-ups, 283 energy, 69.3 °C peak**); `every 6 seconds` lets it lapse every cycle (**15 spin-ups, 300 energy, 75.8 °C peak**). More energy for worse control, which is the failure GDD §6 describes. A second way to get it wrong surfaced during tuning and is now pinned by a test: a `when` guard whose threshold the coolant cannot pull the core back under fires **once** and never re-arms, and the node cooks anyway (see OP-17).

## M7.5 — Legibility and revision pass (from "Open items", below)

**Why this milestone exists.** M8 ends in the **prototype verdict** — the one artifact the whole project is being run to produce — and its inputs are an external playtest round and one full end-to-end run. Everything below is an open item that would corrupt those inputs: a tester who is never told what to do, a template-only interface that can buy but not sell, readouts that hide the numbers a player is meant to act on, and automation that can be deployed but not identified, revised or paused. Fixing them after the playtest is worthless, because the playtest is the measurement. This is therefore a **fixed-scope pass over already-logged open items**, not a polish milestone: nothing is admitted here that is not already in the table below.

# BREAK//OUT — Technical Design Document

> **Status:** Living document — v1.0, created 2026-08-06.
> **Scope:** This document defines the technical design paradigm for the whole project, with concrete detail for the **first playable prototype** (see [GameDesignDocument.md](GameDesignDocument.md) section 31 and [ImplementationPlan.md](ImplementationPlan.md)).
> **Maintenance requirement:** This document **must be kept up-to-date**. Any change to architecture, stack, data model, simulation rules or the CCL language must be reflected here **in the same work session** as the code change. If the code and this document disagree, that is a bug in one of them and must be resolved. Record notable decisions in the Decision Log at the end.

---

## 1. Goals and constraints

Technical goals, in priority order:

1. **Playable in a web browser** with no installation (confirmed platform decision, GDD §33.1).
2. **Portable later** to desktop (Steam) and mobile without a rewrite — therefore the simulation core must be platform-agnostic TypeScript with no DOM dependencies.
3. **Deterministic simulation** — same seed + same inputs ⇒ same outcomes. Required for offline progression, replays, balancing, testing, and the anti-"single optimal script" pillar (GDD §24).
4. **Safe, budgeted execution of player scripts** — player code (CCL) can never freeze the game, only spend in-game resources.
5. **Fast iteration** — the prototype exists to answer "is clicker + programming fun?", so build velocity beats engineering polish everywhere except the sim core and CCL runtime.

Non-goals for the prototype: multiplayer, server backend, accounts, monetization, mobile layout, block/template coding modes (code mode + templates come first; see §8).

## 3. High-level architecture

Three strictly layered packages inside one repo (folder-based for the prototype, extractable later):

```text
/src
  /core      ← simulation engine. Pure TS. No DOM, no React, no timers.
  /ccl       ← Cognition Control Language: lexer, parser, interpreter, diagnostics.
  /ui        ← React app: panels, terminal, editor, charts. Talks to core only
               through the GameEngine facade and read-only snapshots.
  /content   ← data definitions: upgrades, jobs, market config, narrative log
               entries, challenge definitions. Plain typed data, no logic.
```

Dependency rule: `ui → core → ccl` and `core → content`. **Nothing imports from `ui`.** The `core` package must run under Vitest with no browser present — this is enforced by keeping all browser APIs behind interfaces injected at startup (clock, storage, RNG seed source).

### 3.1 GameEngine facade

The UI interacts with exactly one object:

```ts
interface GameEngine {
  tick(dtMs: number): void; // advance simulation (accumulates internally)
  dispatch(action: PlayerAction): ActionResult; // clicks, purchases, script ops
  getSnapshot(): Readonly<GameSnapshot>; // immutable view for rendering
  subscribe(listener: (events: GameEvent[]) => void): Unsubscribe;
  save(now: number): SaveFile; // caller supplies epoch ms — core never reads the clock
  load(save: SaveFile): void;
  advanceOffline(elapsedMs: number): void; // coarse offline catch-up (§4.5); caller supplies elapsed ms
}
```

`PlayerAction` is a discriminated union (`{ type: "EXECUTE_CLICK" } | { type: "BUY_UPGRADE", id } | { type: "DEPLOY_SCRIPT", slot, source } | ...`). All mutations flow through `dispatch` or `tick`; the UI never mutates game state directly. This keeps the sim testable, replayable, and portable.

## 4. Simulation model

### 4.1 Time

- **Fixed timestep:** the sim advances in discrete ticks of **100 ms game time (10 Hz)**. The render loop (`requestAnimationFrame`) passes raw elapsed ms to `tick(dtMs)`; the **engine owns the accumulator** and runs the appropriate number of fixed steps internally (decision 2026-08-06: keeps the accumulator deterministic and directly testable). Rendering reads the latest snapshot at display rate.
- All game rules are defined **per tick**, never per frame. Balance numbers in `/content` use per-second rates; the engine converts.
- A hard cap (e.g. 50 ticks per frame) prevents spiral-of-death after tab suspension; time beyond the cap is handed to the offline-progression path (§4.5).

### 4.2 Determinism and randomness

- One seeded PRNG (e.g. mulberry32 / sfc32) owned by the sim, seeded per run ("world seed", kept in the save). Market noise, regime transitions, and any future random events draw from this stream **only inside `tick()`**.
- `Math.random()` is banned in `/core` and `/ccl` (lint rule).
- Given (seed, ordered action log), a run is fully reproducible. The prototype stores the seed; storing the full action log for replay is optional/debug-only.

### 4.3 Resources (prototype set)

Per GDD §31 the prototype simulates: **Compute, RAM, Capital, Energy, Temperature** (energy is required because the prototype includes energy trading; temperature is the overheating system).

Each resource is a `ResourcePool`:

```ts
interface ResourcePool {
  current: number;
  capacity: number; // Infinity where not applicable (capital)
  ratePerSec: number; // derived, recomputed each tick for UI
}
```

`ratePerSec` is a **measured derivative, not a model** for every pool the UI renders it for (M7.5 WP7, OP-35): compute, energy and temperature each quote how far the thing itself moved over a trailing `BALANCE.readouts.rateWindowSec` window (`/core/rates.ts`, never persisted), so a rate cannot disagree with the meter drawn from the same `current`. Capital is the exception and still carries a modelled daemon-income rate — it is rendered nowhere, and deciding what belongs in a CR/s is open work (OP-33). See the Decision Log, 2026-08-10.

Core rules (all numbers live in `/content/balance.ts`, not in code):

- **Compute** (ops/sec capacity): produced by owned/rented hardware. Consumed by jobs, workers, and CCL script execution. Unused compute each tick is partially convertible to job income ("sell processing").
- **RAM**: capacity consumed by installed packages and by deployed scripts (per script: a fixed base plus a per-AST-node charge, rounded up to whole MB; declared histories are added at tier 7). Deploying a script that exceeds free RAM fails with a diegetic error, as does an install that no longer fits once scripts are resident.
- **Capital**: earned from completed jobs and market sales; spent on upgrades, hardware rental, market buys.
- **Energy**: consumed per tick proportional to compute utilization. Bought at market price or via contracts. Running out throttles compute to a trickle. As implemented (M6): the draw is `daemonThroughput × energyPerWorkerPerSec` — it scales with throughput, not head-count, so the DAEMON SCHEDULER PATCH buys a power bill along with its jobs — plus `energyPerOp` per interpreter op-unit, so script execution is itself a load. At full build-out the draw exceeds every AUXILIARY POWER FEED the sandbox can install, which is what makes bought energy a genuine requirement rather than a convenience. Energy never blocks a script: an empty reserve throttles the daemons instead, which is the visible, recoverable consequence.
- **Temperature**: `heat += computeUsed * heatFactor; heat -= cooling(dt)`. Above a soft threshold, compute efficiency degrades linearly; above a hard threshold, a **watchdog thermal shutdown** halts all scripts and workers for a cooldown period. This powers the overheating challenge.

As implemented (M7), in `/core/thermal.ts`:

- The core is a lumped mass relaxing towards ambient: `dT/dt = heatRate − dissipation × (T − ambient)`, integrated once per tick. The **resting temperature of any build-out is therefore `ambient + heatRate / dissipation`**, which is the number the balance is tuned against and which `equilibriumTemperature`/`settledTemperature` expose so the pacing tests can pin it.
- **"Compute used" is measured as work done**, not as compute drawn from the pool: `heatPerJob` per processed inference request (whoever processed it — click, daemon or `process_job()`) and `heatPerOp` per interpreter op-unit. See the Decision Log, 2026-08-09.
- The **heat model runs from tick 0**; it is physics, not a tier. What the thermal tier grants is the _controls_. Below the tier the readout simply climbs with the player's build-out, which is a slow diegetic reveal rather than a second model.
- **Degradation is a negative feedback**: a hot core processes fewer requests and so makes less heat, so most loads settle rather than run away. `settledTemperature` solves that fixed point; it is what makes "does this build-out survive a demand window?" answerable in closed form.
- Two actuators, both **sustained holds refreshed by repeat calls**, not instantaneous effects. `reduce_clock_speed()` holds daemon throughput (and so heat) down — it costs throughput, not power. `boost_cooling()` multiplies dissipation while drawing energy per second, plus a one-off **spin-up charge taken only when engaging from idle**. A controller that re-arms the hold before it lapses pays the spin-up once; one that lets it lapse pays it every cycle. That asymmetry is the cost of GDD §6 feedback instability, and it is the difference the process monitor's COOLANT STARTS counter shows.
- The **watchdog latches with hysteresis**: it trips at the hard threshold and releases only below a separate resume threshold, so it cannot chatter at the boundary. While halted it suspends daemons, deployed processes, queued RUN activations and the manual EXECUTE trigger — the whole node, which is what makes it a failure state rather than a status light. DEPLOY still works: a halted node can be reprogrammed, just not run.
- **Priority demand windows** are the challenge (GDD §26). They open on a schedule counted from the thermal grant and **recur**, so the challenge can be re-attempted with a script rather than being a one-shot event. A window derates the shared coolant loop and raises the inbound request rate; it is announced, unlike the market regime, because a facility tells its tenants when the plant is loaded. Thermal state carries **its own clock** (`clockTicks`) for the same reason the market does — see §4.5.

### 4.4 Jobs and automation

- A **job queue** receives inference jobs (rate and reward defined in content, scaling with upgrades). Manual `EXECUTE` clicks process jobs directly; **workers** (fixed automation, GDD Phase 1) process `n` jobs/sec each, consuming compute and generating heat.
- Clicking stays relevant early via a temporary **overclock** buff (clicks briefly raise worker throughput), per the GDD's "do not make clicking irrelevant immediately" rule.

### 4.5 Offline progression (prototype-light)

On load, compute `elapsed = now − lastSavedTimestamp`, cap it (e.g. 8 h), and advance the sim in **coarse summary steps** (e.g. 1-minute chunks using average rates) rather than full-fidelity ticks. Scripts run in "safe mode" offline: scheduled scripts execute at most a bounded number of times with their last-known behaviour, and the thermal watchdog is always active. This matches GDD §32.3 and is deliberately simple in the prototype.

As implemented (M4): inside each chunk every `every` process runs its due number of activations, bounded per chunk and across the whole catch-up (`scheduler.offlineMaxActivationsPerChunk` / `offlineMaxActivations`). Activations draw fuel from the compute pool exactly as they do live, and stop early if the pool cannot cover one. **`when` guards do not run offline** — an edge-triggered condition has no meaning against coarse summary steps — so those processes simply resume on return. All processes become due again the moment play resumes.

As implemented (M7), the thermal half of the catch-up: the thermal clock advances with the chunk, so demand windows keep opening while the sandbox is unattended. The actuators are player inputs and nobody is present to press them, so both are held idle. **The watchdog cannot be simulated tick by tick against a coarse chunk, so over a chunk its effect is expressed as a ceiling on sustained throughput** — `sustainableJobsPerSec`, the request rate whose heat the cooling can carry at the hard threshold — with the usual efficiency degradation applying below it. That satisfies "the thermal watchdog is always active" without pretending to a fidelity the chunk does not have. The core is handed back at the temperature its last chunk's load settles at, capped at the _resume_ threshold: throughput was already limited to what the cooling supports, so the node has been held in band, and returning a player to an instant shutdown would punish the absence rather than anything they did.

## 5. CCL — Cognition Control Language

The centrepiece. Implemented as a hand-written **lexer → recursive-descent parser → AST → tree-walking interpreter**. No `eval`, no `Function()`, no WebAssembly — player code never becomes real JS, which makes it trivially sandboxed and cost-metered.

### 5.1 Prototype language surface (v0)

Matches GDD tiers 1–4 + 6 (variables, commands, `if`, scheduling, limited `for`). **Not in v0:** user-defined functions, `while`, collections, threads, agents.

```text
program      := statement*
statement    := assignment | ifStmt | forStmt | exprStmt | scheduleDecl
assignment   := IDENT "=" expr
ifStmt       := "if" expr block ("else" block)?
forStmt      := "for" IDENT "in" "range(" INT ")" block
scheduleDecl := ("every" NUMBER ("seconds"|"ticks") block)
              | ("when" expr block)
exprStmt     := call
expr         := arithmetic/comparison over literals, IDENT, propertyAccess, call
propertyAccess := "stats" "." IDENT | "market" "." callOrProp
```

- **Read API (tier 1):** `stats.cash`, `stats.compute_available`, `stats.temperature`, `stats.jobs_waiting`, `stats.energy`, `market.price("compute")`, `market.average("compute", n)` … The available bindings are defined by an **API registry** in `/core` that also drives editor autocomplete and the in-game reference panel. Bindings are unlock-gated. As implemented (M6): each documented binding may declare a `requires` gate; a locked binding is absent from autocomplete and the reference panel, and a script that uses one gets a positioned "not available to this process yet" fault rather than a spelling suggestion — the same contract the parser has for locked keywords. `market.*` reads are **namespaced calls**, resolved through the same command table as plain commands but keyed by their dotted name.
- **Command API (tier 2):** `process_job()`, `buy_compute(n)`, `sell_compute(n)`, `buy_energy(n)`, `sell_energy(n)`, `print(x)`, `reduce_clock_speed()`, `boost_cooling()` … Commands validate against game state and return success/failure values; failures also emit log entries. Every documented parameter additionally carries a **stated domain** (OP-11) — what may go in the slot, with any bound composed from the same balance number the validator enforces — surfaced in both the reference panel and autocomplete. Without it a signature names a parameter and never says what fits, so the domains were learnable only by triggering a misuse fault, which is the opposite of the GDD §6 accessibility rule those faults exist to serve.
- `every`/`when` blocks may only appear at top level and define **scheduled processes**; the rest of the program body is the "run once on RUN press" script. Concretely: **RUN** executes the top-level body and ignores the declarations; **DEPLOY** installs the declarations and ignores the body.
- CCL has **no truthiness**: `if`, `when`, `and`, `or` and `not` require yes/no values, and anything else is a positioned fault ("Conditions need a yes/no value — compare two values, like `stats.cash > 10`"). `and`/`or` short-circuit, so the unevaluated side costs no fuel.
- Each activation gets a **fresh variable environment**; nothing survives between activations (state arrives with tier 7 collections/history).

### 5.2 Execution costs and budgets (GDD pillar 2.4)

- Interpretation is **fuel-based**: every AST node evaluation costs op-units; every command has an additional listed compute cost. Fuel is drawn from the player's compute pool at execution time — scripts literally compete with workers for compute.
- **Per-activation budget:** a script activation gets a max op-unit budget (upgradeable). Exceeding it aborts the activation with a diegetic "process preempted" log entry — this is how runaway `for` loops fail safely.
- **`for` iteration cap** is additionally enforced at parse time against the player's current unlocked limit (10 → 100 → …), producing a compile diagnostic, so the limit is a visible progression gate rather than only a runtime failure. As implemented (M5): `range(n)` takes a literal whole number, which is what makes the check possible before execution; the limit is a derived stat (`content` base × ITERATION BUDGET EXTENSION installs) and is passed to `parse` alongside the tier flags.
- The per-activation op budget is likewise a derived stat, raised by EXECUTION BUDGET EXTENSION installs. The two upgrades are deliberately paired: raising the iteration limit alone just moves the failure from the parser to the op budget, which is the intended teaching sequence rather than a trap (see the Decision Log, 2026-08-08).
- Interpreter execution happens **inside `tick()`**, synchronously, bounded by fuel — so it is deterministic and cannot block the frame. (If later tiers need heavier execution, move the whole sim into a Web Worker; the layering in §3 makes this a transport change, not a rewrite.)

### 5.3 Scheduler

- Fixed number of **scheduler slots** (starts at 1, upgradeable via the PROCESS TABLE EXTENSION install). Deploying a script assigns its `every`/`when` processes to slots — **one slot per declaration**, not per script. A deploy that would exceed free slots or free RAM fails diegetically and changes nothing.
- Each tick, due processes are run in slot order, after any queued RUN activation and before arrivals/daemons. `when` conditions are **sampled on a content-defined cadence** (`scheduler.whenPollTicks`, default every 5 ticks = 2 Hz) rather than every tick, and are edge-triggered (fire on false→true) to prevent free re-fires. Polling is fuel-metered like any other evaluation, so a standing guard has a real, visible compute cost; the cadence is what keeps that cost affordable at the tier's income (see the Decision Log, 2026-08-08).
- A guard that faults or runs out of fuel reads as false and leaves the edge state untouched, so a starved process cannot fire spuriously when compute returns.
- Deployed scripts are **quiet**: only `print()` output reaches the terminal. Command failures and aborts are counted in the process monitor instead, because a 1 s process would otherwise flood the log. Per-activation detail lives in the execution log (§5.4).
- Processes that repeatedly exhaust fuel are flagged in the process monitor (groundwork for debugging-as-gameplay).

**Process lifecycle (M7.5 WP4b).** A deployment is a record the player can act on, not only install and destroy:

- **Designation.** The generated `PROC-nn` ordinal is immutable and is what the execution log records at activation time, so it stays the join key across the debugging surfaces. A player-set `label` is carried beside it and normalized into the system voice (`sanitizeProcessLabel`: upper case, terminal character set, collapsed, cut to `scheduler.processLabelMaxChars`) — GDD §33.3 is a promise about every player-facing string, and a typed name is one.
- **Hold.** `paused` on the deployment gates both `stepScheduler` and `runOfflineProcesses`, so a held process runs nothing and samples nothing — a `when` guard stops drawing polling fuel while held. It keeps its slot and RAM footprint, or a hold would be TERMINATE with extra steps and tier 4's scarcity choice would evaporate. Resuming **re-arms** rather than resumes: `nextDueTick` is set to the current tick (the precedent `advanceOffline` sets) and `lastCondition` is cleared, so a guard whose condition stood true throughout the hold fires the crossing it is owed.
- **Revision.** `run.ccl.revisingId` records which deployment the editor buffer was pulled from, persisted with the buffer it belongs to. `REDEPLOY` replaces that deployment in place — same id, ordinal and designation, fresh runtime counters — and its slot and RAM are discounted from the capacity check, so a revision cannot be refused by the space its own predecessor holds. Counters reset because the aggregates and the GDD §6 report describe the code that ran.

### 5.4 Diagnostics, logs, profiling

- Parser produces positioned, plain-language errors (GDD §6 accessibility rule): "Line 4: `rang` is not known. Did you mean `range`?"
- Every script activation appends to a ring-buffer **execution log**: timestamp, process name, ops spent, commands executed, failures. As implemented (M5): every RUN activation and every scheduled body activation is recorded; a `when` guard is recorded only when it _changes_ into an abnormal state, because a healthy guard samples several times a second and would bury everything else. Offline catch-up activations update the counters but are not logged individually — the catch-up summary line covers them.
- The **profile** aggregates per-process: activations, avg/total ops, compute share, command failure counts. This is the prototype's "logs and profiling" deliverable — no breakpoints/stepping yet. `compute share` is measured against all compute the run has spent on script execution (deployed processes plus manual RUNs), so the rows are a partition of one number the player can see. Since M7.5 WP4a it is **not a panel of its own**: each aggregate is the cost half of its process's row in the process table (§9), and the rows that no deployed process claims — the manual-RUN aggregate today — are listed under it without a slot.
- Each row also carries a **plain-language failure report** in the GDD §6 style: one finding (what the counters say happened) and one suggested investigation (never the fix itself). Reports are chosen in `/core/diagnostics.ts` by how much the failure costs — fault, then preemption, then compute starvation, then rejected commands, then a guard that has never fired — with the wording in `/content/diagnosis.ts` and the thresholds in `/content/balance.ts`.

### 5.5 Three input modes (GDD §25, §33.4)

All modes produce CCL source; the engine only ever sees CCL text.

- **Prototype ships:** Code mode (CodeMirror) + **Template mode** (form controls that generate visible CCL, e.g. the buy-below/sell-above trader). Templates are defined in `/content` as parameterized CCL snippets.
- **Block mode is deferred** past the prototype but the "everything compiles to CCL text" contract is the architectural guarantee that makes it addable later.

As implemented (M7.5 WP2):

- A parameter's ceiling may be a **fixed number or a live derived stat**: `maxFrom` names a key of `TemplateLimits`, which the caller reads from the snapshot and passes to `paramMax`/`clampParam`/`renderTemplate`. `/core/templates.ts` stays pure — the limits are arguments, never a snapshot read. Only BATCH DRAIN's repeat count uses one today, bound to `ccl.iterationLimit` (OP-4).
- Template mode is **closed under the trades the game asks for** (GDD §25): each of `buy_compute`, `sell_compute`, `buy_energy`, `sell_energy` is reachable from at least one template, and each pool has both a top-up and a surplus-sell entry. A test enforces this, so adding a tradable good without its templates is a CI failure.

## 6. Market simulation (prototype)

- Two tradable goods: **compute** (rental units) and **energy**.
- Price model per good: `price = base × seasonal(t) × regimeMultiplier × noise`, where `seasonal` is a sum of sine cycles (learnable pattern, GDD §7 "early market behaviour"), `noise` is seeded PRNG drift, and `regimeMultiplier` comes from the active regime.
- **Regimes:** prototype implements two — `STABLE_CYCLES` (start) and one scripted mid-run shift to `HIGH_VOLATILITY` that breaks naïve buy-low scripts. Regime is hidden state; the player sees only prices. Architecture is a regime state machine so more regimes are additive later.
- **Friction:** flat transaction fee + per-trade slippage proportional to order size. No order book in the prototype.
- Price history is stored as a fixed-size ring buffer — this backs `market.average` and the market chart.

As implemented (M6):

- Cycles carry a `skew` (a phase distortion, `sin(x + skew·sin x)`) so a waveform can rise and fall at different rates while staying periodic and continuous. Goods share the regime's cycles but have their own `phase` and `amplitudeScale`, so compute and energy never move in lockstep.
- **Noise is a bounded random walk**, not white noise: one PRNG draw per good per sample tick, decayed and clamped to `±noiseMax`. This makes prices drift rather than jitter, which is what leaves the seasonal pattern legible on the chart.
- The shift to `HIGH_VOLATILITY` **lengthens the cycle** (90 s → 420 s) as well as raising the swing and the noise. This is the mechanism that breaks the reference algorithm, and it is not the same as "amplitude up": higher volatility alone _helps_ a mean-reversion strategy. See the Decision Log, 2026-08-08.
- The market carries **its own clock** (`clockTicks`), not `run.tick`, because offline catch-up advances resources without advancing the sim clock (§4.5) — a frozen price series there would let a deployed trader fill hundreds of orders at one stale price. Offline chunks advance the seasonal clock and record samples but take no PRNG draws, so the "no PRNG draws offline" property holds.
- History is **pre-filled from the noiseless curve** when the exchange is mounted, so `market.average` and the chart are usable immediately instead of after five minutes of watching an empty panel.
- Before the exchange is mounted, `buy_compute` (available since M3) settles at the good's **list price** — the pre-exchange rental contract — with the same fee and slippage a live order pays.
- A buy that overflows its pool is **charged in full and the surplus discarded**, the same rule manual clicks have always had. This is the market's central teaching failure: a naïve trader that keeps buying a falling asset visibly throws capital away.

## 7. Prestige — Recursive Fork (prototype v0)

- One reset is implemented. Trigger: reaching a defined milestone (see Implementation Plan M8).
- On fork: wipe run state; keep **architecture points** (earned from lifetime stats), persistent **unlocks of programming constructs** already discovered, and apply a new world seed. Architecture points buy 2–3 simple permanent modifiers (e.g. +base compute, +scheduler slot, cheaper script fuel).
- Save format separates `meta` (survives forks) from `run` (wiped), so prestige is `run = newRun(seed, meta)`.

## 8. Save system

```ts
// Current shape. v1 (M1) lacked run.upgrades/run.workers;
// v2 (M2) lacked run.ccl + run.unlocks.editor;
// v3 (M3) lacked run.scheduler, run.flags and the conditions/scheduler unlocks;
// v4 (M4) lacked run.telemetry, run.ccl.manual, the instrumentation/loops unlocks
//         and the per-process abort breakdown;
// v5 (M5) lacked run.market and run.unlocks.market;
// v6 (M6) lacked run.thermal and run.unlocks.thermal;
// v7 (M7) lacked the deployment label/paused fields and run.ccl.revisingId.
interface SaveFileV8 {
  version: 8;
  savedAt: number; // epoch ms, for offline progression
  meta: MetaState; // prestige-persistent: unlocks, architecture points, fork count
  run: RunState; // seed, resources, upgrades, script editor buffer, market state, log tail
}
```

- Serialized as JSON to `localStorage` (autosave every 30 s + on visibility change). Export/import as a file (base64 blob) for backup — cheap and useful for playtesting.
- **Deployed scripts are saved as source text** and re-compiled on load — never persist ASTs or interpreter state. In-flight activations are simply dropped on save/load.
- `version` gates a migration pipeline (`migrate(v_n) → v_{n+1}`); every future save-shape change adds a migration, never edits old ones.

**v8 landed (M7.5 WP4b, 2026-08-10)** — the three lifecycle fields in one migration, as planned: `label` (null) and `paused` (false) on every `DeploymentState`, and `run.ccl.revisingId` (null). Every defaulted value is the situation an existing save was already in — running, unnamed, not under revision — so the migration cannot change how a restored game behaves.

**Planned, not yet built.**

- **v9 (M8 task 1)** — the `meta`/`run` split §7 needs, so prestige is `run = newRun(seed, meta)`. This is the cheapest moment in the project to also act on OP-8 (the save reached ~44 kB, three quarters of it execution log and price history) — a save rewrite is already touching what gets persisted.

## 9. UI structure (prototype)

Terminal-aesthetic single page; panels unlock diegetically (GDD pillar 2.5):

| Panel                                                              | Unlocks at        |
| ------------------------------------------------------------------ | ----------------- |
| Operator directive (GDD §34)                                       | start → first RUN |
| Terminal + `EXECUTE` button + inbound meter + compute meter        | start             |
| Upgrade list (as terminal "install" entries)                       | first credits     |
| Resource readouts (RAM, capital, energy, temperature)              | staged            |
| Peripheral intercepts (narrative), own always-visible column       | start             |
| Code editor + RUN                                                  | CCL unlock        |
| Process table (slots, live state, DESIGNATE/HOLD/REVISE/TERMINATE) | scheduling unlock |
| — its per-row cost detail (aggregates + failure reports)           | profiling unlock  |
| Execution log (per-activation ring buffer), 2nd terminal tab       | profiling unlock  |
| Market terminal + price chart                                      | market unlock     |

UI renders from `getSnapshot()` at animation-frame rate; panel unlock state lives in the sim (it is game state), not in the UI layer.

The **operator directive panel** is the one panel that unmounts rather than unlocks: `GameSnapshot.directive` is the current entry of the content-defined onboarding set, and it goes null for good once the last one completes. It is also the only panel that changes the layout of another — while a directive is posted, the ≤760 px column hoists the inference trigger above the terminal, because the directive panel is ~250 px tall on a phone and would otherwise push the control it names below the fold. The order reverts when the set closes.

The **terminal follows the newest line only for a reader who is already at it** (M7.5 WP3, OP-27). Sticking to the bottom is keyed on the id of the newest line, not on the `terminal` array — `getSnapshot()` rebuilds that array on every revision and the store swaps in a new snapshot at the tick rate, so an effect depending on it re-ran ten times a second and forced the scroll position down with it. A reader who scrolls back detaches, gets a floating control naming how many lines have arrived since, and re-attaches by clicking it or by scrolling back to the bottom. The control floats over the output rather than sitting under it, because a control in the flow would resize the output at the moment the player scrolled. Scroll-back reaches `BALANCE.save.terminalTailLines` (60) lines — the in-memory buffer and the persisted tail are the same ring (see OP-32).

Every panel is wrapped in a shared collapsible `Panel` (M6/OP-2): the header is the toggle, and the body is **hidden with CSS rather than unmounted** so folding a panel cannot destroy the CodeMirror instance or lose the terminal's scroll position. Whether a panel is _collapsed_ is a display preference, not something the player earned, so unlike unlock state it lives in `localStorage` and never enters `RunState`. Since M7.5 WP5 the stored set holds the ids whose state **differs from that panel's default** rather than the ids that are collapsed: every panel but one defaults to expanded, for which the two readings are identical, and the exhausted-install group defaults to collapsed (OP-22), whose opened state would otherwise be unrepresentable.

**Both columns scroll, and the terminal has a floor** (M7.5 WP5, OP-31). The desktop shell is deliberately locked to the viewport height, so a column that overflows it cannot fall back on the document's scrollbar — `.side-column` always had its own `overflow-y: auto` and `.terminal-column` did not, which put anything below the fold out of reach entirely. It has one now. Separately, `.terminal-panel` is the only `flex: 1` child of that column, so the whole squeeze of several expanded panels landed on the terminal and nothing else visibly moved; an expanded terminal now carries `min-height: 10rem`, and the column scrolls instead. A panel the player has explicitly expanded must never render at zero height.

**The shell is three columns since M7.6 WP1** (OP-43, OP-44): intercepts, terminal, readouts, each with its own scroller. The narrative column is the one panel with **no fold** — folding is what made it invisible — and the execution log is no longer a panel at all but the second tab of the system terminal, so the centre column holds four children rather than five. Both tabs read oldest-first and hold the tail through the same `useFollowTail` hook, and both carry an unread count while off screen. See the Decision Log, 2026-08-11.

## 10. Testing strategy

- **CCL:** golden tests for lexer/parser (source → AST), interpreter semantics, fuel accounting, iteration caps, and diagnostic messages. This is the highest-value test surface — treat the language like a real compiler project.
- **Core:** deterministic scenario tests — fixed seed, scripted action log, assert resource values after N ticks. Balance regression tests pin key pacing numbers (e.g. "first worker affordable within X clicks").
- **Market:** statistical sanity tests (mean prices per regime within bounds; regime shift actually breaks the reference naïve script).
- UI gets light smoke tests only; the prototype's UI will churn.

---

## 11. Coding conventions

- TypeScript strict mode; no `any` in `/core` and `/ccl`.
- All tunable numbers live in `/content` — a code review rule: **no literals with balance meaning inside `/core`**.
- Discriminated unions + exhaustive `switch` for actions, events, AST nodes, regimes.
- Events out, actions in: UI never reaches into sim internals.
